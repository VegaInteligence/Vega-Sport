# PannaData fixture index refresh

The macOS runner fetches the live `opta_fixtures.parquet`, pins its version and runs only the technical fixture index. It removes the source files from local temporary storage. The AWS bridge only carries the PostgreSQL protocol. This path does not load events, publish canonical facts or cover the other PannaData assets.

## Modes on main

- `preflight` checks the live release, digest and cutoff without AWS or PostgreSQL credentials. The dedicated draft-branch push runs this same check with a read-only GitHub token.
- `connect` uses its own AWS role and a PostgreSQL login that has only CONNECT. It verifies the pinned endpoint, TLS, identity, read-only transaction and absence of DML permissions. It fetches no source. With `cancellation_probe=true`, the job waits for cancellation for up to 90 seconds after attesting the connection.
- `refresh` requires `PANNA_MANUAL_REFRESH_ENABLED=true` for an explicitly dispatched write. The separate `PANNA_DAILY_ENABLED=true` flag enables the scheduled write at 04:17 UTC. Both are absent by default. Keep the schedule disabled until the approved dataset coverage is delivered. Manual runs consume the live digest and current UTC cutoff. For replay, verify that two runs occurred on the same UTC date and selected the exact same digest. The second writes 0 data rows. If the source changes between runs, it is a delta run rather than a replay.

## Deploy and verify after review

1. Apply migration 005. Create `vega_panna_fixture_daily` with two connections and no memberships or elevated privileges, then apply `fixture-login-grants.sql`. Use a separate `vega_panna_fixture_connect` login with no memberships, schema usage or DML rights, one connection and default read-only transactions. The operator verifies effective SQL privileges before issuing either secret. Use the distinct SSM parameters in the corresponding permissions files. DSNs must target the private host with `sslmode=verify-full`. If using a CMK, scope the KMS grant to the exact parameter and role.
2. Deploy `bridge.yml` with the private RDS hostname, reviewed ARM64 image digest, ECR execution role and existing SNS alert topic. Reuse the authorized network for the DB and AWS control plane. No service runs permanently. Enable alarm actions after acceptance, verify the subscription and test a missing-heartbeat alert in the isolated environment. Before enabling the schedule, verify that at least two recent runtime windows do not overlap maintenance.
3. ZIP only `launcher.py`. Deploy Python 3.12 or later with `launcher.handler`, 100-second Lambda timeout and reserved concurrency of one, and publish the reviewed version as `vega-v2-panna-daily-launcher:live`. Set exact `TASK_DEFINITION` and `BRIDGE_NETWORK`. Replace the three placeholders in the launcher IAM policy. The workflow has no direct ECS RunTask authority. The bridge container has a 30-minute maximum life. A timeout or empty inventory during cleanup needs an independent ECS/SSM readback.
4. Create the main-only `v2-panna-refresh` environment. Set `PANNA_REFRESH_ROLE_ARN`, `PANNA_CONNECT_ROLE_ARN`, and `PANNA_BRIDGE_LAUNCHER` as environment variables. The job resolves the RDS hostname from its instance-scoped AWS read after assuming the role. Give the two roles the exact main OIDC trust and individual permissions. Keep both write flags unset. Run the main preflight and connect modes through the GitHub dispatch. Use an isolated transport scope or a transport-only main release for pre-merge proof. Any separate branch scope gets only a pinned transport identity, the read-only login and no writer parameter or role.
5. Verify the exact allowed SSM session can connect and closes cleanly. Verify denial from a wrong repo/ref/environment/workflow or for a different document, shell, untagged task, neighboring secret, or direct RunTask. Repeat on cancellation and verify the task and session have actually stopped. Deliberate cancellation sends no SQL writes. An observed TTL fallback bounds use if the runner disappears.
6. After coordinator approval of the first fixture write, enable the manual flag only, dispatch `refresh`, and independently confirm the ledger pin and cutoff. Replay on the same day and digest. Publication of `FixtureIndexVerified` after successful close is an operational heartbeat. The CloudWatch missing-data alarm tracks 26 one-hour buckets. Before enabling the cron, obtain validation of the complete agreed dataset scope, enable monitoring and verify the first real `schedule` event Mac offline.

For `CHURN_GUARD`, first compare the source generation and affected segment ratio with the previous receipt. Resume outside this automation only after deciding that the upstream changes are expected. The job never auto-overrides the guard. It enforces 10,000-row chunks, a 420-second loader budget, and periodic RDS storage/CPU checks. The 1 GiB peak allowance requires target measurement. The existing loader does not enforce a per-second rate.

Run `PYTHONPATH=backend python infra/aws/panna/daily.py` locally after installing the requirements for a non-AWS fixture probe. An empty manifest passed to preflight returns exit 1 and `ASSET_MISSING`.

## Durable queue mode

On first installation, run queue.sql as the database owner. Create a separate LOGIN for the queue with CONNECT to vega_v2, USAGE on panna_sync, SELECT/INSERT/UPDATE on its two tables and USAGE on its identity sequence only. Store the verify-full DSN at the dedicated queue parameter in the reviewed IAM policy. This role does not need any Panna sink grants. The existing fixture login and future action/identity logins remain distinct. Add only the relevant handler credentials after grants, migrations, producers and receipts are reviewed.

The scheduled mode is sync, triggered twice hourly. Each UTC day and after 22 hours it checks discovery due against the RDS cursor; repeated ticks do not re-plan an already known unit. SQL claims are bounded and fenced, interrupted product runs are found through their immutable queue ID in the loader ledger, and the loader's own idempotent retry handles partial chunks. A manual dispatch of sync uses the existing write authorization flag, with no automatic enablement. The GitHub preflight for this branch is credential-free; neither the schedule nor manual sync can write from the branch.

The fixture adapter calls the normal Panna CLI. The actions adapter calls the real S3 CLI for one pinned whole asset at a time but cannot be reached until both the action role is provisioned and the pinned identity stage verified. For larger action work, validate RSS/decode footprint and add reviewed shard proof before changing that unit shape. The future resolver hooks into the same queue via panna.identity.run_hosted_identity and must use its regular reviewed entrypoint. The adapter accepts only a positive durable run ID with state verified, exact fixture_sha256 and ISO as_of for this job. The resolver must attest new club/edition decisions and control transaction effects itself. Without it, identity units stay handler_pending and actions stay dependency_pending. Unconfigured source channels are also shown as open. The sync never claims full coverage.

The optional revision-scoped idle hint can skip a hosted check until the next known due time (at most two hours), only for a schedule event and while this workflow is the sole queue writer. Leave PANNA_IDLE_HINT disabled until failed/discarded ticks and explicit dispatch are tested together. The separate OptaLatestInventoryVerified alarm detects a missing verified inventory; it does not attest completeness of other source channels. Alarm actions and both write flags are left off at rollout preflight.
