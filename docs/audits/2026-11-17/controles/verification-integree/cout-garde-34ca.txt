# Coût local des protections de références

Le 18 novembre 2026, sur le code `34ca3b5b382d7a6a06da9d051170096ba1d700e8`, le retrait normal d’une fixture vide a pris **43,84 ms** avec les gardes et **37,83 ms** dans le témoin. L’écart médian apparié est de **5,69 ms** sur quatre paires après préchauffage. Les deux tables volumineuses contiennent chacune 2 282 608 lignes. Dans cette distribution, PostgreSQL 18.6 utilise l’index primaire pour vérifier l’absence du match, même sans prédicat de saison. Le plan de la fonction de découverte complète rend 8,16 ms, 5 903 accès à des blocs en cache et zéro lecture disque lors du passage instrumenté. [Détail des répétitions](receipt.json) · [Plans du retrait et des deux index](withdraw-plans.json)

La matérialisation de **170 332 notes** par la vraie fonction `power.write_match_grades` prend **2,381 s** protégée et **0,886 s** témoin, pour **15 352** notes effectivement changées. Trois paires donnent un surcoût médian apparié de **1,477 s**, rapport des médianes **2,69**. L’EXPLAIN d’une exécution distincte attribue **1 471,67 ms et 170 332 appels** au trigger de migration 141 sur l’upsert. Un input inchangé passe aussi par le trigger BEFORE INSERT avant que ON CONFLICT examine les valeurs déjà présentes. Le débit observé justifie de tester une protection ensembliste de coût inférieur si elle conserve intégralement le refus des références tombstonées et les garanties de concurrence. ## Protocole

- L’instantané RDS à lecture répétable de **22 h 09 min 32 s UTC** fournit les effectifs de notes valides par édition. Le chargement local conserve les 2 282 608 lignes, les six saisons de stockage et les effectifs exacts des 301 éditions positives. Les équipes, joueurs, matchs, minutes et valeurs sont simulés, avec 32 places par match, 71 480 matchs de contributions et 32 000 joueurs effectivement utilisés. Les autres familles volumineuses de la base RDS n’ont pas été dupliquées. Le catalogue est celui du code candidat. 340 tombstones de matchs extérieurs à ce jeu sont synthétiques. [Distribution utilisée](repartition-source.csv.gz) · [Relation et paramètres de l’instance](result.json)
- Une migration vers 151 est exécutée dans une nouvelle base. Les données sont ensuite clonées dans une seconde base physique. Au moment de mesurer, l’écriture de notes utilise le vrai rôle `vega_calc` et le retrait utilise `vega_collect`. Le témoin de l’écriture désactive le seul trigger d’archive présent sur les tables de sortie de `write_match_grades`. Les droits et contraintes FK des grades restent actifs. Les deux bras reçoivent les mêmes tuples, donnent les mêmes nombres et la même somme vérifiée des notes, puis annulent la transaction de mesure. Le temps inclut COPY via psycopg, upsert, suppression des notes obsolètes et agrégats d’édition. Il exclut le COMMIT final, la reconstruction amont des variables, la calibration, la publication globale du classement et l’écriture des lignes de puissance de match. Le chargement de ces dernières restitue leur volume pour les contrôles de dépendance.
- Le retrait passe par `sources.run_due` avec le vrai fichier de résultats et un calendrier contrôlé retirant une fixture. La fixture n’a aucun enrichissement ni prévision. Dans le témoin, seule la découverte générale des dépendances est neutralisée et le trigger 151 de clés fournisseur est désactivé. Le code de prise de possession du parent et de ses clés demeure actif. Le retrait emploie DELETE, qui ne déclenche pas le trigger 151 d’INSERT/UPDATE. Le chiffre caractérise ce parcours, sans isoler le coût d’une insertion de clé ni le temps d’installation de la migration. Le cas d’un report avec prévision qui bloque est démontré séparément dans la contre-lecture.
- Deux bases physiques sous PostgreSQL 18.6 à 127.0.0.1:55439, un seul client actif à la fois, parallèle SQL désactivé pour les sessions du benchmark, work_mem 32 Mio et shared_buffers 128 Mio. Les bras alternent pour limiter le biais d’ordre. Les plans instrumentés sont mesurés séparément. Les ratios ne sont pas des prévisions de latence RDS ou de temps total du worker. Aucune mesure lourde n’a été effectuée en production. [Espace et plafonds avant chargement](budget.md) · [Déroulement](timeline.txt)

## Reproduire

Depuis un dépôt Git contenant l’objet examiné sur le Mac, utiliser le Python du dossier de preuves et le PostgreSQL 18.6 de test. Le harnais extrait le code en dehors du worktree. Le témoin désactive un trigger uniquement dans les tables de sa base privée. Les bases du benchmark sont identifiées par UUID et supprimées en fin d’exécution. La sortie `absent_after` doit valoir `true` et les deux bras doivent conserver les effectifs attendus.

```sh
E="/Users/lemonnierhugo/.codex/visualizations/2026/11/17/01a1e6f1-9c43-7b81-a52e-3ee15c953578/production-architecture-review"
D="$E/delivery/corrections-34ca/cout"
PYTHONDONTWRITEBYTECODE=1 "$E/ci-clean/bin/python" -B "$D/bench.py"
python3 "$D/summarise.py"
VEGA_BENCH_SIX=1 PYTHONDONTWRITEBYTECODE=1 "$E/ci-clean/bin/python" -B "$D/bench.py"
python3 "$D/six-saisons/summarise.py"
```
