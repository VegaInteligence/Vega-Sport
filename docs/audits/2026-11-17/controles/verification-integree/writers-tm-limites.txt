## Lecteurs et propriété

- **Valeurs de marché.** `write_values` supprime les dates Transfermarkt absentes de la liste dès qu’il existe au moins un point valide. La route `/api/player-market-values?id=…` lit `api.player_market_values`, puis la courbe consomme ces points. Le test envoie le validateur de la réponse complète après chaque rafraîchissement. Il établit la disparition publique du point par HTTP 200 et la rotation du validateur.
- **Blessures.** `write_injuries` remplace les épisodes du joueur. Pour servir `/api/players/{id}/injuries`, `api.player_injury_reads` exige une lecture sans `error_code`. Un échec de schéma masque donc des épisodes valides encore persistés. Le client affiche cette route dans l’historique et la disponibilité. Les tests établissent la différence entre HTTP 200 avec liste vide et HTTP 404. Ils ne mesurent pas le rendu du navigateur.
- **Effectifs.** `write_squad` remplace le couple club/saison. Le planning `enqueue` lit directement la table des effectifs pour découvrir les nouveaux profils. Le rejeu vérifie le nouveau planning et le maintien d’une unité déjà inscrite. Le rapprochement `link_players` utilise aussi les appartenances par saison selon l’inspection du code. Aucune route HTTP ne lit `core.provider_squads` sur ces deux SHA. La recherche de clubs `fetch_search → write_search` constitue un second point d’écriture de cette table. Elle passe une liste non vide sans test de complétude et peut donc remplacer un effectif par un sous-ensemble. Cette portée est établie par lecture du code. Le rejeu dynamique emprunte le trajet normal de rafraîchissement `squad`.

## Rejouer

Le poste de vérification a utilisé Python 3.12, psycopg 3.2.12, Node.js 26.4.0 et PostgreSQL 18.6. Les scripts exigent des noms de bases de test sur l’interface locale et créent une base neuve distincte par exécution. Démarrer PostgreSQL 18 sur `127.0.0.1` avec un répertoire temporaire, et utiliser les dépendances Node déjà installées pour le lecteur API. Exécuter depuis le dossier de cette preuve avec les variables `VEGA_TM_REPO`, `VEGA_TM_NODE_MODULES`, `VEGA_TM_LOCAL_PORT` et `VEGA_TM_LOCAL_USER` propres à cet environnement.

```sh
tm_scratch=$(mktemp -d)
for tm_sha in 34ca3b5b382d7a6a06da9d051170096ba1d700e8 202f24c09eb4c8fb87d7190939bafbf09cb00393; do
  mkdir -p "$tm_scratch/$tm_sha"
  git -C "$VEGA_TM_REPO" archive "$tm_sha" backend/vega backend/sql backend/api/src dashboard/shared |
    tar -x -C "$tm_scratch/$tm_sha"
  ln -s "$VEGA_TM_NODE_MODULES" "$tm_scratch/$tm_sha/backend/api/node_modules"
  python3 -B rejouer.py "$tm_scratch/$tm_sha/backend" "$tm_sha" \
    "postgresql://$VEGA_TM_LOCAL_USER@127.0.0.1:$VEGA_TM_LOCAL_PORT/vega_v2_tm_$tm_sha" \
    "$tm_scratch/$tm_sha-resultats.json"
done
```
